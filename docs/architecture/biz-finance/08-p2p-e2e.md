# P0-07 P2P 第一条端到端链路设计 v1

> 状态：Draft v1  
> 归档日期：2026-08-26

## 1. 目标

P0-07 不再新增平台级抽象，而是把 P0-01 ~ P0-06 串成 Matrix 第一条真实可验证的采购到付款（P2P）端到端链路。

目标链路：

```text
BusinessPartner(SUPPLIER)
  ↓
PurchaseOrder
  ↓
PurchaseReceipt
  ↓
PurchaseAcceptance
  ↓
PurchaseInbound
  ↓
AP Estimate
  ↓
SupplierInvoice
  ↓
3-Way Match
  ↓
AP Formal
  ↓
PaymentApplication
  ↓
PaymentOrder
  ↓
BankTransaction
  ↓
AP Settlement
  ↓
Accounting Event
  ↓
Voucher
  ↓
GL
```

P0-07 的设计目标不是一次性实现采购全域，而是明确第一条真实业务链中：

- 每一张单据是什么。
- 每一步由哪个服务负责。
- 哪一步允许下推下一单。
- 哪一步产生 Business Event。
- 哪一步产生财务结果。
- BOTP / Reconciliation / Write-off 分别负责什么。
- 哪些现有 Matrix 能力保留兼容，哪些后续迁移。

## 2. 需求依据

### 2.1 采购履约

业财一体 1.0 对采购履约明确区分：

```text
供应商发货
→ 采购收货检验
→ 采购验收
→ 采购入库
```

验收完成后，根据验收结果进行实物入库并形成采购入库单，记录合格或让步接收的库存数据。

因此 Matrix 不把“收货”“验收”“入库”压缩成一张单据。

### 2.2 对账、发票、应付

业务方案明确：

```text
采购入库
→ 与供应商对账
→ 供应商开票
→ 发票签收
→ 财务应付挂账
```

应付管理进一步明确：

```text
采购入库单审核
→ 暂估应付

采购发票审核
→ 正式应付

财务应付单审核
→ 采购成本 / 应付 / 进项税核算
```

### 2.3 付款申请

付款计划与申请需要：

```text
按合同账期梳理到期应付
→ 结合资金预算排定付款计划
→ 关联资金计划与付款排期
→ 匹配合同 / 发票 / 验收 / 入库资料
→ 提交付款申请
→ 审核完整性 / 合规性 / 预算余量
```

### 2.4 支付、回单、核销

资金支付要求：

```text
付款单制单 / 复核
→ 资金支付预算校验
→ 资金支付审核
→ 银行支付
→ 获取银行回单 / 流水
→ 匹配付款单并反写已付款
→ 应付核销
→ 生成付款凭证
```

因此“付款单审核通过”不能直接等价于“已付款”。银行支付结果和银行流水/回单才是支付完成的关键事实。

## 3. P0-07 对前序设计的一处语义修正

前序 P0 文档示例使用过：

```text
PURCHASE_RECEIPT_CONFIRMED
→ 暂估应付 / Accounting Event
```

在将源业务流程串成完整 P2P 后，该示例需要修正。

正式语义统一为：

```text
PURCHASE_RECEIPT_CONFIRMED
= 实物已经收货，不代表已经验收、入库，不触发财务暂估

PURCHASE_ACCEPTANCE_CONFIRMED
= 检验/验收结论已经确认，不直接触发暂估

PURCHASE_INBOUND_CONFIRMED
= 合格/让步接收数量已正式入库，是暂估应付和采购入库核算的触发事实
```

因此第一条财务触发链修正为：

```text
PURCHASE_INBOUND_CONFIRMED
        ↓
AP Estimate
        ↓
PURCHASE_INBOUND_ESTIMATE_RECOGNITION
        ↓
Accounting Rule
        ↓
Voucher
```

该修正不改变 P0-03 / P0-04 的架构，只校正第一个事件类型的业务含义。

## 4. 服务边界

### 4.1 base-service

负责：

```text
BusinessPartner
Supplier Role
Supplier Bank Account
Supplier Tax Profile
Settlement Terms
```

采购单据只引用 `businessPartnerId`，不复制维护供应商主数据。

### 4.2 erp-service

P0-07 首次真正启用 `erp-service`，第一阶段只实现 procurement 子域：

```text
erp-service
└─ single.cjj.erp.procurement
   ├─ order
   ├─ receipt
   ├─ acceptance
   ├─ inbound
   └─ invoice
```

后续再增加：

```text
purchase-request
sourcing
contract
return
claim
supplier-collaboration
```

### 4.3 botp-service

负责业务/财务单据转换和上下游关系：

```text
PO → Receipt
Receipt → Acceptance
Acceptance → Inbound
AP → PaymentApplication
PaymentApplication → PaymentOrder
```

不负责：

```text
3-Way Match
AP balance
银行到账确认
Accounting Rule
Voucher
```

### 4.4 fi-service

负责：

```text
AP Estimate
AP Formal
PaymentApplication
PaymentOrder
BankTransaction
AP Settlement
Reconciliation
Accounting Event
Voucher
GL
```

`fund` / `cashier` 当前代码基本仍是占位，P0-07 需要开始形成真正资金交易领域。

## 13. 正式应付 AP Formal

处理：

```text
SUPPLIER_INVOICE_CONFIRMED
        ↓
P2PFinancialOrchestrator
```

如果存在对应暂估：

```text
① 识别原 AP Estimate
② 按原暂估实际结果生成全额冲回
③ 将原 Estimate 标记 REVERSED
④ 创建 Formal AP
⑤ 创建两个 Accounting Event
```

Accounting Event：

```text
PURCHASE_ESTIMATE_REVERSAL
PURCHASE_AP_RECOGNITION
```

暂估冲回不能用当前最新规则重新计算，必须基于原核算结果/原凭证快照反向生成。

Formal AP：

```text
fpayable_type = FORMAL
foriginal_amount = 发票含税应付金额
fopen_amount = original - settled - reserved
```

账期：

```text
fdue_date
```

由合同/付款条件解析。

### 14.1 目标表

```text
      ↓
```

```text
famount

fpayment_method

```

### 14.4 Allocation

```text
fid
fpayment_application_id
fpayable_id
fapplied_amount
freserved_amount
fstatus
```

### 14.5 付款申请校验

必须校验：

```text
AP = OPEN / PARTIAL_SETTLED
businessPartner 一致
currency 一致
申请金额 <= AP open amount
合同/发票/验收/入库资料完整
资金计划存在（要求场景）
预算余量足够
```

其中预算规则由 Budget Domain 判断，PaymentApplication 只消费结果。

### 14.6 Reservation

创建/提交付款申请时进行预占：

```text
AP open 10000
reserved 0

Application A reserve 6000
→ available = 4000
```

并发申请必须锁定 AP 或使用 CAS/乐观锁。

Matrix 当前 `BotpArapIntegrationService` 已经存在：

```text
SELECT FOR UPDATE
amount - applied - reserved
reserve
remaining
```

这套预占语义保留，并迁入新的 PaymentApplicationService。

### 14.7 BOTP

```text
AP
 ── GENERATES / SETTLEMENT_REQUEST ──>
PaymentApplication
```

现有 BOTP 兼容入口在迁移期继续可用。

```text

```


### 15.4 BOTP

```text

      ↓
PaymentOrder
```

```text
NOT_EXECUTED
PARTIAL
COMPLETE
```

### 17.2 规则

```text
settledAmount <= payable.openAmount
```

正式执行 Settlement 时：

```text
1. 锁定 Payable
2. 校验 open amount
3. 写 Settlement Entry
4. 更新 settled/open amount
5. 释放对应 PaymentApplication reservation
6. 更新 payable status
```

结果：

```text
open > 0  → PARTIAL_SETTLED
open = 0  → SETTLED
```

### 17.3 与 Reconciliation 的关系

Reconciliation 输出：

```text
建议哪个 Payment / BankTransaction
匹配哪个 AP
建议金额多少
```

Settlement 才执行余额变化。

## 18. PAYMENT_COMPLETED 事务边界

由于 Payment、AP Settlement、Business Event Outbox 都在 `matrix_fi`，P0 建议在同一本地事务内：

```text
Bank reconciliation matched
        ↓
PaymentOrder = PAID
        ↓
Create AP Settlement
        ↓
Update AP open amount
        ↓
Release reservation
        ↓
append PAYMENT_COMPLETED Outbox
```

这样不会出现：

```text
付款显示已完成
但应付没有核销
```

或：

```text
应付已经核销
但付款仍显示处理中
```

## 21. BOTP Relation 图

业务转换：

```text
PurchaseOrder
  ↓ FULFILLS
PurchaseReceipt
  ↓ GENERATED_FROM
PurchaseAcceptance
  ↓ GENERATED_FROM
PurchaseInbound
```

财务执行：

```text
AP
  ↓ GENERATES
PaymentApplication
  ↓ GENERATES
PaymentOrder
```

不通过 BOTP 生成：

```text
AP Estimate / Formal
Voucher
BankTransaction
AP Settlement
```

原因：

- AP 是业务事件驱动的财务结果。
- Voucher 是 Accounting Event 驱动的会计结果。
- BankTransaction 是外部银行事实。
- Settlement 是核销领域结果。

## 24. 现有 Matrix 兼容迁移

### 24.1 当前 AR/AP

当前：

```text
BizfiFiArapDoc
```

同时承载：

```text
AP
AP_ESTIMATE
AP_PAYMENT_APPLY
AP_PAYMENT_PROCESS
...
```

这适合作为早期通用模型，但已经无法清晰表达 P2P 各阶段的独立状态、分录、核销和银行交易。

目标：

```text
matrix_fi_ap_payable
matrix_fi_payment_application
matrix_fi_payment_order
matrix_fi_bank_transaction
matrix_fi_ap_settlement
```

迁移策略：

1. 新 P2P 链优先写新模型。
2. 旧 `/payable/**` 页面和 API 第一阶段可通过 Facade 兼容。
3. 旧 `BizfiFiArapDoc` 不再继续增加新的 P2P 专属字段。
4. 新模型稳定后再专项迁移历史 AR/AP 数据。

### 24.2 当前 BOTP AP → Payment Application

现有 `BotpArapIntegrationService` 已实现：

```text
AP 必须 AUDITED
SELECT FOR UPDATE
计算 amount - applied - reserved
防止超下推
创建付款申请
反写 reserved / remaining / pushStatus
```

这套并发控制和预占思想保留。

新模型中迁移为：

```text
PaymentApplicationService.reservePayable()
```

BOTP Adapter 调新的领域 Service，不再直接操作历史 `BizfiFiArapDoc`。

### 24.3 当前 AP_PAYMENT_PROCESS

当前文档把付款处理复用通用 AR/AP 字段，并在审核后直接按固定科目生成凭证。

P0-07 目标改为：

```text
PaymentOrder Audit
≠ Payment Completed
≠ Voucher Generated
```

必须等银行支付事实确认后，形成 Settlement 和 `PAYMENT_COMPLETED`，再由 Accounting Engine 生成凭证。

## 25. 关键一致性规则

### 25.1 数量链

```text
PO Quantity
>= Receipt Quantity
>= Accepted/Inbounded Quantity
```

是否允许超收由采购策略决定，BOTP 本身不硬编码。

### 25.2 验收

```text
received
=
qualified + concession + rejected
```

### 25.3 入库

```text
inbound quantity
<= qualified + concession - already inbound
```

### 25.4 Invoice

正式应付前：

```text
3-Way Match = MATCHED
OR approved Resolution
```

### 25.5 Payment Application

```text
application allocation
<= AP available amount
```

其中：

```text
available
= original - settled - reserved
```

### 25.6 Settlement

```text
settlement
<= AP open amount
```

### 25.7 Bank

```text
PaymentOrder = PAID
```

必须有银行确认/人工授权的支付结果，不允许仅以“付款单审核通过”判断。

## 28. 反向 / 异常验证

必须覆盖：

1. PO 100，只允许合法数量下推 Receipt。
2. Receipt 100，Acceptance 80 合格 + 20 不合格，只允许 Inbound 80。
3. Inbound 撤销后，暂估应付必须冲销而不是物理删除。
4. Invoice Qty > Inbound Qty，3-Way Match 必须阻断。
5. 同一 Invoice 重复确认，不能重复生成 Formal AP。
6. AP open 10000，两并发付款申请各 7000，只能一笔成功或第二笔按剩余额度失败。
7. PaymentOrder 审核后但银行未扣款，不得变 PAID、不得核销 AP。
8. BankTransaction 重复推送，只能保留一个银行事实。
9. Bank match 后 Settlement 失败，PaymentOrder 不能单独提交 PAID。
10. Payment Completed 消息重复，不能重复生成付款凭证。
11. Payment Reverse 必须恢复 AP open amount，并产生反向会计事件。
12. 所有节点可从 Voucher / GL 反向穿透到 PO。

## 30. P0-07 验收标准

设计验收：

- 收货、验收、入库语义分离。
- 暂估触发点修正为入库确认。
- 三单匹配成为正式应付前置门槛。
- AP 与 Payment Application 支持部分付款和并发预占。
- PaymentApplication 与 PaymentOrder 分离。
- 银行事实才决定 Payment PAID。
- Reconciliation 不直接改余额。
- Settlement 才改变 AP open amount。
- Accounting Engine 才决定会计科目和凭证。
- 整条链支持 Document/BOTP/Event/Accounting/Voucher/GL 穿透。

实现验收最终以 Smoke Test 和异常用例全部通过为准。
