# P2 O2C（Lead-to-Cash / Order-to-Cash）设计 v1

> 状态：Draft v1  
> 日期：2026-08-27  
> 目标分支：dev

## 1. 定位

P1 已完成采购到付款（P2P）业务覆盖与 Procurement BOTP v1 收口。

根据 Matrix 业财一体业务域总图，下一阶段进入：

```text
P2 = O2C
CRM
→ 合同
→ 销售
→ 发货
→ AR
→ 收款
```

目标主链：

```text
Lead
→ Opportunity
→ Quote / Tender
→ SalesContract
→ SalesOrder
→ SalesDelivery
→ SalesAcceptance
→ CustomerInvoice
→ Formal AR
→ Collection
→ BankTransaction
→ AR Settlement
→ Accounting Event
→ Voucher
→ GL
```

本阶段沿用 P0/P1 已建立的：

- Business Event / Transactional Outbox
- BOTP Document / Relation / Entry Relation
- Accounting Event / Rule / Voucher
- Reconciliation
- Workflow
- Scheduler

不建设第二套平台基础设施。

## 2. 当前代码现状

### 2.1 Customer / Supplier

前端已有：

```text
/customer/**
/supplier/**
```

页面和 API。

后端当前仍由：

```text
BaseDataWorkflowController
→ ConcurrentHashMap
```

临时承载 Customer / Supplier。

因此：

- 服务重启数据丢失。
- Customer / Supplier 没有统一法人主体。
- 无法提供稳定 BusinessPartner ID 给 CRM / Sales / AR。
- 不满足 P0 BusinessPartner 设计。

P2 必须先完成该基础事实，不能继续在 CRM 中复制一套 Customer。

### 2.2 CRM / Sales

当前 `erp-service` 尚无正式：

```text
crm
sales
sales-contract
```

业务包。

因此 P2 从零建立经营域对象，但继续在同一个 `erp-service` 中先领域模块化，不提前拆新微服务。

### 2.3 AR

当前 `fi-service/ar` 已有历史：

```text
bizfi_fi_arap_doc
AR / AR_ESTIMATE / AR_SETTLEMENT
```

并有：

- 应收页面
- 账龄
- 信用预警
- 结算处理
- BOTP 兼容能力

但历史实现存在：

```text
counterparty = String
审核后直接硬编码科目生成 Voucher
```

P2 不删除旧 AR 页面和接口，但新 O2C 正式应收不能继续复制这种耦合。

正式方向：

```text
CustomerInvoice / Delivery Business Event
→ FI Inbox
→ Formal AR
→ Accounting Event
→ Accounting Rule
→ Voucher
```

## 3. 服务边界

### base-service

负责：

```text
BusinessPartner
PartnerRole
Customer/Supplier compatibility facade
Contact
Address
BankAccount
TaxProfile
SettlementProfile
Organization availability
```

客户信用策略不放入基础主体。

### erp-service

新增：

```text
crm
├─ lead
└─ opportunity

sales
├─ quotation
├─ contract
├─ order
├─ delivery
├─ acceptance
└─ invoice
```

负责经营事实，不直接创建 AR/Voucher。

### fi-service

负责：

```text
AR Formal
Collection
Bank Transaction
AR Settlement
Credit exposure
Accounting Event / Voucher
```

历史 `BizfiFiArapDoc` 第一阶段保留兼容。

### botp-service

负责：

```text
Opportunity → Quote
Quote → SalesContract
SalesContract → SalesOrder
SalesOrder → Delivery
Delivery → Acceptance
CustomerInvoice → AR/Collection trace
```

仅确定性转换自动执行。

商机输赢、报价审批、合同谈判等决策不由 BOTP 自动替代。

## 4. BusinessPartner / Customer 原则

P2 第一项先兑现 P0 BusinessPartner 设计。

统一主体：

```text
BusinessPartner
  ├─ CUSTOMER
  └─ SUPPLIER
```

同一法人只有一个 Partner。

交易单据保存：

```text
businessPartnerId = 权威引用
businessPartnerCode / Name = 历史快照
```

旧：

```text
/customer/**
/supplier/**
```

接口保持兼容。

## 5. CRM

### Lead

表达尚未完成客户资格确认的线索。

核心事实：

```text
source
name
company
contact
owner
status
estimatedValue
nextActionDate
```

生命周期：

```text
NEW
→ QUALIFYING
→ QUALIFIED
→ CONVERTED

异常：
DISQUALIFIED / CLOSED
```

Lead 不强制要求 Customer 已存在。

### Opportunity

表达已经具备可追踪商业价值的商机。

必须关联：

```text
BusinessPartner(Customer)
owner
expectedAmount
expectedCloseDate
stage
probability
currency
project / cost center（适用时）
```

商机阶段变化是经营事实，不直接产生财务结果。

## 6. Quote / Tender

报价是销售约价事实，不等于合同。

至少包含：

```text
BusinessPartner
Opportunity
Material / Service
Quantity
UnitPrice
TaxRate
Validity
DeliveryTerm
PaymentTerm
```

支持：

```text
DRAFT
SUBMITTED
APPROVED
SENT
ACCEPTED
REJECTED
EXPIRED
```

客户接受报价仍不直接产生 AR。

## 7. SalesContract

销售合同是客户、价格、税率、账期、履约边界的权威来源。

关系：

```text
Opportunity / Quote
→ SalesContract
→ SalesOrder
```

合同分录预留：

```text
orderedQuantity
deliveredQuantity
invoicedQuantity
settledAmount
```

并通过领域事务 / BOTP Relation 可解释地反写。

## 8. SalesOrder

订单只允许基于有效客户及有效商业条件创建。

关键状态拆分：

```text
fstatus
fapproval_status
fdelivery_status
finvoice_status
fsettlement_status
fclose_status
```

信用规则只作为销售订单提交/审核的 Gate，不与主数据生命周期混用。

## 9. Delivery / Acceptance

销售履约明确拆：

```text
SalesOrder
→ SalesDelivery
→ CustomerAcceptance
```

是否触发收入 / 应收，由业务方案对应场景和正式会计策略决定，不在销售服务硬编码。

第一阶段采用：

```text
CustomerInvoice confirmed
→ Formal AR
```

避免“发货即应收”覆盖所有企业场景。

## 10. CustomerInvoice → AR

CustomerInvoice 属于 ERP 销售业务发票事实。

审核/确认后发布：

```text
CUSTOMER_INVOICE_CONFIRMED
```

FI 消费后：

```text
Formal AR
→ SALES_AR_RECOGNITION
→ Accounting Rule
→ Voucher Draft
```

AR 保存：

```text
businessPartnerId
sourceDocument
originalAmount
settledAmount
reservedAmount
openAmount
dueDate
status
accountingStatus
```

## 11. Collection / Bank / Settlement

正式链：

```text
CollectionApplication / CollectionOrder
→ BankTransaction
→ AR Settlement
```

银行指令/收款计划不能直接等价为到账。

到账事实以银行流水/回单为准。

核销：

```text
AR.openAmount
→ settlement allocation
→ PARTIAL_SETTLED / SETTLED
```

## 12. P2 实施顺序

```text
P2-IMP-01 BusinessPartner + Customer/Supplier Persistence
P2-IMP-02 Lead / Opportunity
P2-IMP-03 Quote / Tender + SalesContract
P2-IMP-04 SalesOrder
P2-IMP-05 Delivery / CustomerAcceptance
P2-IMP-06 CustomerInvoice → Formal AR
P2-IMP-07 Collection / BankTransaction / AR Settlement
P2-IMP-08 O2C BOTP Completion + Frontend E2E
```

顺序理由：

1. 没有稳定 Customer ID，CRM / Contract / Sales / AR 都会继续依赖字符串往来方。
2. 先形成经营事实，再接履约和财务。
3. AR 新模型必须通过 Business Event / Accounting Event 接入，不直接在 ERP 生成 Voucher。
4. BOTP 在业务对象稳定后统一收口，避免反复改 Relation 语义。

## 13. P2-IMP-01 验收边界

P2-IMP-01 完成后必须满足：

- Customer / Supplier 不再存于进程内 Map。
- 同一 BusinessPartner 可同时拥有 CUSTOMER + SUPPLIER。
- `/customer/**`、`/supplier/**` 前端接口保持兼容。
- 生命周期与审批状态分离。
- 已审核资料不能直接删除。
- 数据持久化到 `matrix_base`。
- 服务重启数据不丢失。
- 后续 CRM/Sales 可引用稳定 `businessPartnerId`。
- 不修改 `matrix-prp`。

## 14. 非目标

P2 v1 暂不实现：

- CPQ 高级定价引擎
- 自动投标评分
- 复杂返点/返利
- 渠道分销
- 订阅计费
- 多级经销商结算
- 高级催收策略
- 税务申报
- 制造生产计划

这些不应阻塞第一条 O2C 闭环。
