# Matrix 项目规划

> 更新日期：2026-07-22  
> 当前阶段：业务平台能力建设与公共基础设施补齐

## 1. 项目定位

Matrix 是面向企业业务与财务场景建设的平台型系统。当前在持续开发以下核心子系统：

- IM 推送系统
- 定时任务调度系统
- BOTP 业务下推系统
- OpenAPI 开放平台
- 业务工作流系统

下一阶段不再单纯增加新的独立业务模块，而是优先建设上述系统共同依赖的可靠性、可观测性、安全和运维基础设施，降低重复开发成本，形成统一的平台内核。

## 2. 下一阶段建设目标

下一阶段围绕以下七项基础能力展开：

1. 统一执行台账
2. 统一事件规范和 Event SDK
3. Outbox、幂等、重试、死信和重放
4. 全链路 TraceId
5. Prometheus、Grafana 和日志平台
6. 统一审计日志
7. 配置和密钥隔离

完成后，IM、调度、BOTP、OpenAPI 和工作流系统应共用统一的执行、事件、追踪、监控和安全能力。

---

## 3. 统一执行台账

### 3.1 建设目标

对平台内所有异步任务和跨系统执行过程进行统一记录，形成统一查询、补偿和运维入口。

### 3.2 覆盖范围

- IM 消息推送
- BOTP 业务下推
- 定时任务执行
- 工作流节点执行
- OpenAPI 异步请求
- RabbitMQ 事件消费
- 后续新增的批处理和集成任务

### 3.3 核心能力

- 统一执行状态
- 执行次数与最大重试次数
- 请求参数和响应结果
- 错误码、错误信息和异常堆栈摘要
- 开始时间、结束时间和执行耗时
- 下次重试时间
- 超时任务识别
- 人工重试、终止和忽略
- 按业务单号、执行 ID、事件 ID 和 TraceId 查询
- 执行主记录与每次尝试明细分离

### 3.4 建议状态

```text
PENDING
RUNNING
SUCCESS
WAITING_RETRY
RETRYING
FAILED
CANCELLED
TIMEOUT
```

### 3.5 设计原则

统一执行台账只负责技术执行状态和运维信息，各业务系统仍保留自己的业务状态，避免技术状态与业务状态耦合。

---

## 4. 统一事件规范和 Event SDK

### 4.1 建设目标

统一 Matrix 平台的事件模型和 RabbitMQ 使用方式，避免各服务自行定义消息结构、交换机命名和异常处理逻辑。

### 4.2 统一事件字段

```text
eventId
eventType
eventVersion
sourceService
tenantId
bizType
bizId
occurredAt
traceId
correlationId
idempotencyKey
data
```

### 4.3 Event SDK 能力

- 标准事件对象
- 事件发布接口
- 事件消费接口
- Exchange、Queue 和 RoutingKey 命名规范
- JSON 序列化与反序列化
- TraceId、租户和业务上下文自动传递
- 消费端幂等校验
- 消费异常分类
- 消费结果写入统一执行台账
- 统一日志和指标埋点
- 事件版本兼容机制

### 4.4 使用约束

业务服务原则上通过 Event SDK 发布和消费事件，不直接散落使用 RabbitTemplate 和原生 RabbitMQ 配置。

## 5. Outbox、幂等、重试、死信和重放

### 5.1 Outbox

业务数据与待发送事件在同一个本地事务中写入，避免业务数据提交成功但 MQ 消息未发送的问题。

处理流程：

```text
业务事务写入业务表和 Outbox
→ Outbox 发布器扫描待发送记录
→ 发布到 RabbitMQ
→ 成功后更新发送状态
→ 失败后进入等待重试
```

需要支持：

- 批量扫描
- 多实例竞争
- 乐观锁或抢占式状态更新
- 发送超时恢复
- 最大重试次数
- 历史数据归档

### 5.2 幂等

生产端：

- 使用 `idempotencyKey` 防止同一业务重复创建任务或事件
- 数据库唯一索引兜底

消费端：

- 使用 `eventId` 或业务幂等键去重
- 业务执行和消费记录尽可能处于同一事务
- 重复消息返回已处理结果，不重复执行业务

### 5.3 重试

统一定义：

- 最大重试次数
- 固定间隔或指数退避
- 可重试异常
- 不可重试异常
- 下一次执行时间
- 重试耗尽后的处理方式

每次重试必须写入执行明细，并记录触发原因。

### 5.4 死信

任务超过最大重试次数或发生不可恢复错误后进入死信状态。

死信管理应支持：

- 查看原始消息和失败原因
- 查看全部执行记录
- 关联业务单据
- 修改允许修正的参数
- 人工重新投递
- 标记忽略
- 批量处理

### 5.5 重放

支持按照以下条件重放：

- EventId
- ExecutionId
- 业务单号
- 事件类型
- 租户
- 消费者
- 指定时间范围

重放前必须执行权限校验和幂等检查，并记录操作人、原因和结果。

## 6. 全链路 TraceId

### 6.1 建设目标

保证一次业务请求经过多个服务、异步线程和 RabbitMQ 后仍可定位完整执行链路。

典型链路：

```text
Gateway / OpenAPI
→ 业务服务
→ 工作流
→ 定时任务
→ RabbitMQ
→ BOTP 下推
→ IM 推送
```

### 6.2 统一上下文字段

```text
traceId
spanId
correlationId
tenantId
bizId
executionId
eventId
```

### 6.3 实现范围

- 网关自动接收或生成 TraceId
- HTTP 请求头传递
- OpenFeign 拦截器自动传递
- RabbitMQ Message Header 自动传递
- 线程池和异步任务上下文传递
- 日志 MDC 自动写入
- 执行台账保存 TraceId
- 前端管理台按 TraceId 查询完整链路

### 6.4 约束

所有跨服务调用和异步执行必须保留原 TraceId，不允许在中间节点无条件生成新的链路标识。

## 7. Prometheus、Grafana 和日志平台

### 7.1 Prometheus 指标

基础运行指标：

- JVM、内存和 GC
- CPU 和系统负载
- 线程池状态
- 数据库连接池
- HTTP 请求量、错误率和耗时
- RabbitMQ 连接、消费速率和积压

核心业务指标：

- IM 推送成功率和失败率
- BOTP 下推成功率和失败率
- 调度任务准时执行率
- 工作流节点成功率和平均耗时
- OpenAPI 请求成功率、P95 和 P99
- 重试任务数量
- 死信数量
- 超时任务数量
- 各事件类型消费积压量

### 7.2 Grafana 看板

规划以下看板：

- 平台运行总览
- 微服务健康状态
- IM 推送监控
- BOTP 下推监控
- 调度系统监控
- 工作流监控
- OpenAPI 调用监控
- RabbitMQ 监控
- 数据库和连接池监控
- 重试、超时和死信监控

### 7.3 日志平台

统一接入 Loki 或 Elasticsearch，日志格式至少包含：

```text
timestamp
level
serviceName
instanceId
traceId
spanId
tenantId
bizId
executionId
eventId
userId
message
exception
```

日志中禁止输出密码、Token、AppSecret、数据库密码、AI API Key、完整银行卡号和其他敏感信息。

### 7.4 告警

首批告警规则：

- 服务实例不可用
- OpenAPI 错误率持续升高
- RabbitMQ 队列积压超过阈值
- 死信数量增长
- 调度任务延迟执行
- IM 或 BOTP 成功率低于阈值
- 数据库连接池耗尽
- JVM 内存或 GC 异常

## 8. 统一审计日志

### 8.1 建设目标

建立独立于普通运行日志的审计体系，回答“谁在什么时间，以什么身份，对什么资源执行了什么操作”。

### 8.2 重点审计操作

- 登录和退出
- 用户、角色和权限变更
- OpenAPI 应用和密钥管理
- 配置修改
- 密钥修改和轮换
- IM 人工重发
- BOTP 人工重推
- 调度任务启停和手工触发
- 工作流撤回、跳过、终止和转办
- 死信处理和事件重放
- 数据导入、导出和敏感数据查看

### 8.3 建议字段

```text
auditId
tenantId
operatorType
operatorId
operatorName
applicationId
operationType
resourceType
resourceId
beforeData
afterData
requestIp
device
traceId
operationTime
operationResult
failureReason
operationReason
```

### 8.4 约束

- 普通用户不可修改审计记录
- 业务管理员不可物理删除审计记录
- 敏感字段必须脱敏
- 重试、重放和人工补偿必须填写原因
- 支持按用户、业务资源、时间和 TraceId 检索

## 9. 配置和密钥隔离

### 9.1 普通配置

普通配置继续由 Nacos 管理：

- 服务地址
- 超时时间
- 重试次数
- 批处理大小
- 线程池参数
- 限流阈值
- 功能开关
- 调度参数
- 非敏感业务参数

### 9.2 敏感配置

以下内容必须从普通配置和代码仓库中分离：

- 数据库密码
- Redis 密码
- RabbitMQ 密码
- JWT 签名密钥
- OpenAPI AppSecret
- 邮件和短信平台密钥
- AI API Key
- 第三方系统 Token
- 加密私钥和证书密码

### 9.3 建设能力

- 开发、测试和生产环境隔离
- 密钥加密存储
- 最小权限访问
- 密钥版本管理
- 密钥定期轮换
- 密钥访问审计
- 配置变更记录和回滚
- 配置灰度发布
- 服务启动时动态注入

### 9.4 约束

任何生产密钥不得提交到 GitHub，也不得以明文写入 `application.yml`、Docker Compose 或普通数据库字段。

## 10. 开发阶段安排

### 阶段一：可靠执行基础

优先级：P0

- 统一执行主表和执行明细表
- 统一执行状态机
- Outbox 表和发布调度器
- 生产端和消费端幂等
- 自动重试与退避策略
- 死信管理接口
- 单任务人工重放

阶段目标：解决消息丢失、重复执行、失败不可恢复和执行过程不可查询的问题。

### 阶段二：事件和链路统一

优先级：P0

- 统一事件协议
- Event SDK
- RabbitMQ 发布和消费封装
- HTTP、Feign、MQ 和异步线程 TraceId 传递
- 执行台账与事件记录关联
- 按 TraceId 查询完整链路

阶段目标：消除各子系统之间不统一的消息格式和链路断点。

### 阶段三：可观测和运营

优先级：P1

- Spring Boot Actuator 统一配置
- Prometheus 指标采集
- Grafana 核心看板
- 统一日志格式和日志平台
- 核心异常告警
- 异常任务管理页面

阶段目标：实现系统状态可见、异常可发现、链路可定位。

### 阶段四：安全治理

优先级：P1

- 统一审计日志
- 敏感配置清理
- 配置和密钥分离
- 环境隔离
- 密钥轮换
- 重放、重试和配置修改权限控制

阶段目标：实现高风险操作可审计、敏感信息不泄露、关键配置可治理。

## 11. 验收标准

本阶段完成后应满足：

- 任意异步任务均可在统一执行台账中查询
- 任意平台事件均有唯一 EventId 和幂等键
- 业务事务成功后，待发送事件不会因 MQ 短暂异常永久丢失
- 消费者重复接收消息时不会重复执行业务
- 可恢复异常能够自动重试
- 最终失败任务能够进入死信中心
- 授权管理员能够对失败任务进行人工重放
- 一次跨系统调用能够通过 TraceId 查询完整链路
- Grafana 能展示核心系统成功率、耗时、积压和异常数量
- 高风险人工操作均有不可篡改的审计记录
- GitHub 和普通配置文件中不存在生产密钥
- IM、BOTP、调度、工作流和 OpenAPI 复用统一基础能力

## 12. 当前最高优先级

当前开发优先级按以下顺序执行：

1. 统一执行台账
2. Outbox 和消费幂等
3. 重试、死信和重放
4. 统一事件规范与 Event SDK
5. 全链路 TraceId
6. Prometheus、Grafana 和日志平台
7. 统一审计日志
8. 配置和密钥隔离

在上述基础能力稳定之前，新增业务系统应优先复用公共能力，避免继续建设独立的消息表、重试表、审计表和链路追踪逻辑。
