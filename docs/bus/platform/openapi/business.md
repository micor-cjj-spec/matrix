# Matrix 开放平台业务设计

## 1. 业务目标

为外部业务系统提供受控的 Matrix 数据访问能力。第一期只开放财务凭证只读能力，不开放新增、修改、审核、过账、冲销和删除。

## 2. 核心对象

- API 定义：由开发侧注册，描述稳定的外部路径、版本、方法和权限范围。
- 外部应用：一个接入系统对应一个应用，独立持有 AppKey 和 AppSecret。
- API 授权：描述应用可以调用哪些已发布 API。
- 数据权限：第一期支持凭证状态和最大历史月份；组织、账簿权限待凭证模型补齐对应字段后扩展。
- 调用日志：记录 requestId、应用、API、耗时、状态和错误摘要，不记录密钥和完整敏感正文。

## 3. 调用链

外部系统 -> Gateway -> openapi-service -> fi-service 内部 OpenAPI 适配器 -> 凭证领域服务。

Gateway 对 `/api/open-api/**` 不执行内部用户 JWT 校验；openapi-service 必须执行 AppKey、HMAC-SHA256 签名、时间戳、Nonce、防重放、IP 白名单、授权和限流校验。

## 4. 第一期开口

- `fi.voucher.list`：分页查询凭证。
- `fi.voucher.detail`：查询凭证详情。
- `fi.voucher.lines`：查询凭证分录。

默认只允许查询 `POSTED` 状态。应用授权可以进一步收紧，但不能放宽到 API 定义之外。

## 5. 发布流程

1. 开发人员在代码和 SQL 中注册 API 定义。
2. 管理员在前台创建外部应用，系统只在创建时返回一次明文 AppSecret。
3. 管理员为应用授予 API，并设置数据权限、有效期、IP 白名单和流控策略。
4. 外部系统按照签名规范调用。
5. 管理员通过调用日志排查失败、超时和频控问题。

## 6. 边界

- 前台不能配置任意内部 URL、Bean、方法或 SQL。
- 对外 DTO 与内部实体隔离，数据库字段变化不能直接破坏外部协议。
- 第一阶段只支持 GET 请求；写入型 API 后续必须增加幂等键、状态查询、补偿与对账。
